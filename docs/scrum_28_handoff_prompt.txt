MAIN MISSING INCREMENT

Implement the user-facing status-tracking workflow without taking ownership of unrelated approval, planning or completion stories.

1. CORRECT THE FRONTEND STATUS MODEL

frontend/lib/event-requests.ts currently accepts only Draft and Submitted.

Align it with the backend statuses:

- Draft
- Submitted
- Under Review
- Changes Requested
- Approved
- Planning
- Confirmed
- Completed
- Cancelled
- Rejected

Prefer one shared frontend status type or constant mapping to avoid duplicated string logic.

2. CORRECT THE ORGANISER TRACKING TABS

The organiser page currently has All, Draft, Submitted and Completed tabs, but:

- Submitted matches only the exact Submitted value.
- Later active statuses are not grouped properly.
- Completed is hardcoded as empty.

Recommended tabs:

- All
- Draft
- Submitted
- In Progress
- Completed

Recommended grouping:

- Draft: Draft
- Submitted: Submitted
- In Progress: Under Review, Changes Requested, Approved, Planning, Confirmed
- Completed: Completed
- Keep Cancelled and Rejected visible in All, or add a clearly labelled Closed tab only if Jira requires it.

Confirm the expected grouping against SCRUM-28's Jira acceptance criteria before finalising it.

3. ADD AN ORGANISER PROGRESS DISPLAY

Add a reusable status-progress component to the organiser's request card or read-only request detail view.

It should:

- Clearly display the current status.
- Explain the current stage in plain language.
- Avoid suggesting that later stages have occurred.
- Handle rejected, cancelled and changes-requested states explicitly.
- Be accessible on keyboard and screen readers.
- Work on smaller screens.

A full comments or activity timeline is outside this increment unless SCRUM-28 explicitly requires status history.

4. ADD COORDINATOR REQUEST DISCOVERY

The current API lists requests only for the owning organiser. Coordinators cannot discover their assigned requests unless they already know the request UUID.

Add a scoped endpoint such as:

GET /event-requests/assigned-to-me

Requirements:

- Requires an authenticated event_coordinator.
- Returns only requests for which the caller is the latest assigned coordinator.
- Does not expose other coordinators' assignments.
- Supports multi-role users.
- Returns predictable empty and service-error responses.
- Does not allow the browser to supply a coordinator ID.

If the coordinator queue belongs to a different Jira story, document it as a dependency instead of silently adding it to SCRUM-28.

5. ADD A MINIMAL COORDINATOR FRONTEND

Provide a coordinator workspace that:

- Lists requests assigned to the authenticated coordinator.
- Opens a read-only request detail view.
- Shows the current status.
- Offers “Start review” only when the request is Submitted.
- Hides or disables the action after the request leaves Submitted.
- Handles empty, loading, forbidden and unavailable-service states.

Prefer a separate route such as /coordination/requests, while reusing shared request-detail and status components.

6. REVIEW ATOMIC AUTHORIZATION

The existing review service checks the latest assignment and changes the status in separate database requests. A reassignment could theoretically happen between those operations.

Assess whether the assignment check and Submitted to Under Review update should be moved into one server-side database function or transaction that verifies:

- The current status is Submitted.
- The caller is the latest assigned coordinator.
- The status is changed exactly once.
- A failed check causes no status change.

Document the trade-off if this cannot be completed in the current increment.
