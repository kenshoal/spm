## Approved contract

As an Event Organiser or the currently assigned Event Coordinator, I want to view chronological event-request status history so I understand how it reached its current stage and who performed each transition.

The requester approved the reviewed seven criteria and recommendations on 10 October 2026 (“okay follow your recommendation”). Jira wording is retained; the interpretations below are recorded here, not silently written back to Jira.

- **AC1:** Creation and each actual status change record exactly one immutable history entry in the same transaction.
- **AC2:** Each entry records the event, previous status (nullable initially), new status, acting user and role or system source, and timestamp.
- **AC3:** Refused, forbidden, rolled-back and repeated actions without a status change record no entry. Ordinary edits and clarification responses that leave status unchanged also record none.
- **AC4:** History is chronological, deterministically ordered, and its latest entry agrees with the current event status.
- **AC5:** The owner/current coordinator can read history; same-organisation colleagues follow SCRUM-39 non-Draft read-only access. Unrelated users cannot read it, and no history-write API is exposed.
- **AC6:** Current creation/submission/review/resume/cancellation/completion workflows use one recording contract. Future transition owners must adopt it; this story does not implement SCRUM-35 decisions, SCRUM-40 automation, SCRUM-58 planning or SCRUM-60 safety.
- **AC7:** Organiser and coordinator details show an accessible activity timeline, with loading, empty and unavailable states.

Existing events receive a labelled **History recording started** baseline with their current status and actual installation time, system source and no invented earlier actor/transitions. History cannot be independently updated/deleted; deleting an unsubmitted Draft discards its history with it. This is not permanent archival retention.

## Actors, transitions and persistence boundary

Owner can see their Draft and non-Draft history; the current coordinator can see their assigned request; same-organisation organisers see only non-Draft requests. Former/unassigned coordinators, other organisations and missing memberships do not gain access. History has no browser table access or mutation API. Stored actor IDs are shown without adding an identity-display-name lookup.

Current writers are creation as Draft/direct Submitted, owner Draft→Submitted, assigned coordinator Submitted→Under Review, review decisions Under Review→Changes Requested/Approved/Rejected, answered Changes Requested→Under Review, eligible live state→Cancelled and Confirmed→Completed. Cancellation's source partition is Submitted/Under Review/Changes Requested/Approved/Planning/Confirmed. Clarification responses and ordinary edits retain status and add no history. Shared trigger/helper metadata boundaries apply to manual/current and named system actions. Future SCRUM-35/40/58/60 transitions consume that contract but their stories remain excluded.

Event/status/history writes and related business writes commit or roll back together. History is immutable except an authorised unsubmitted Draft discard cascade. Baselines state only known current status at installation, with no invented earlier transitions. A later transition after a completed read can naturally make any page stale; AC4-X5/X6 concern conflicting statuses within the same rendered response.
