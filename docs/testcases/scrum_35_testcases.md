## Requester-approved non-date approval increment — 21 October 2026

**Historical 21 October scope superseded the earlier broad approval prohibition for that build.** The requester authorised independent implementation of non-date approval on base `c8e082f`, following the approved apply-then-flag contract (PO discussion #2408 and caller ownership #2578). Jira's original six acceptance criteria remain unchanged. Existing rejection remains supported; this is not a full-story Done claim.

The current assigned coordinator may approve a Pending proposal on an Approved or Planning event when its entire proposed field set is a nonempty subset of `expected_attendance`, `venue_requirements` and `equipment_requirements`. Apply the exact supported values, retain the actual coordinator/time/optional note and raise the existing SCRUM-64 per-domain review flags and durable review delivery work in one transaction. Recheck assignment, Pending status, event eligibility and the proposal's base event version under the event lock. Date, mixed date/non-date and registration proposals remain wholly unavailable. They must not partially apply. No date mapping, rebooking, registration change or new confirmation workflow is included.

The existing SCRUM-64 writer records one actual event-update UUID shared by the affected reviews. It does **not** directly bind those reviews to `change_request_id`; this increment does not introduce that additional contract. The saved proposal, base event version and saved decision retain change provenance. Event lifecycle/status/history, bookings, reservations, requirements, equipment, assignments, existing review records and prior jobs must remain unchanged apart from the approved fields/version, proposal audit and newly raised reviews/jobs. A no-op or refused/repeated action has no such effects.

**Outcome contract:** after a complete saved Approved response, attempt `event_change_approved` for the stored organiser with payload `{event_request_id, change_request_id, reason}` (reason may be null). Its stable ID is UUID5 with `NAMESPACE_URL` and name `event-change-approved:<change_request_id>`. Only HTTP `202` is accepted. Failed or unexpected delivery cannot mask a successful saved approval. No durable organiser-notice retry/outbox is promised. A malformed upstream Pending response is a safe `502` (`Event change decision unavailable`) and causes no approval notice.

**Stable IDs:** AC3-H1, AC3-P1 and AC6-N1 now exercise approved non-date application and stale protection. AC2-N2 continues to protect unsupported date/mixed/registration approval, rather than all approval. Existing rejection IDs remain active. AC4-X1 now permits supported approval alongside rejection; its existing rejection recovery assertions are retained. The old no-approval UI partition uses a mixed-date proposal. No historical execution record below is rewritten as current evidence.
